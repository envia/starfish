This chapter documents every boundary at which the Starfish web browser engine ("lightweight web engine", README.md line 3) talks to the outside world: the C++ embedding API, network-listening debug/cast endpoints, wire protocols used as client or server, the IDL-generated JavaScript platform surface, external service integrations, and how errors cross each of these boundaries.

## Embedder API

The public C++ embedding surface lives in the `inc/` directory and is exposed under the `LWE` namespace with the `LWE_EXPORT` visibility macro (defined at the top of [`LWEWebView.h`](src:inc/LWEWebView.h#L23)). All public classes hide their implementation behind an opaque [`LWEDelegateRef`](src:inc/LWEWebView.h#L49) (`std::unique_ptr<void, std::function<void(void*)>>`). `inc/PlatformIntegrationData.h` supplies the value types used by this API, e.g. [`KeyValue`](src:inc/PlatformIntegrationData.h#L7), [`TTSMode`](src:inc/PlatformIntegrationData.h#L253) and [`WebSecurityMode`](src:inc/PlatformIntegrationData.h#L258).

## API Endpoints

All network-listening endpoints are debug or cast-service features, each behind a compile-time flag ([`STARFISH_ENABLE_CDP`](src:src/core/cdp/CDPServer.h#L20), [`STARFISH_ENABLE_INSPECTOR`](src:src/core/inspector/Inspector.h#L20), [`STARFISH_ENABLE_CAST_SERVICE`](src:src/core/modules/cast/CastConfig.h#L20), `STARFISH_ENABLE_DEBUGGER` at [`initDebuggerIfNeeds`](src:src/binding/ScriptWrappable.cpp#L1431)).

## Web Platform API Surface (IDL)

JavaScript bindings for spec-defined web interfaces are generated from IDL at CMake configure time. README.md states: "JS bindings for spec-defined interfaces are generated from `src/**/*.idl` at cmake configure time (see `build/binding.cmake`)" (README.md lines 55-58).

- The repository contains **418** `.idl` files under `src/` (`find src -name "*.idl" | wc -l` → 418).
- [`binding.cmake`](src:build/binding.cmake#L28) collects them with `FILE (GLOB_RECURSE STARFISH_BINDING_IDL_FILES ${STARFISH_ROOT}/src/*.idl)`, hashes an mtime signature of all inputs, and — when the signature changes — runs the generator via [`EXECUTE_PROCESS`](src:build/binding.cmake#L68): `${PYTHON_EXECUTABLE} ${STARFISH_ROOT}/binding_generator/scripts/starfish_code_generator.py ${STARFISH_ROOT}/src/ ...`, staging output into `starfish_generated/binding_test/generated/` before promoting changed files. A [`generate_binding`](src:build/binding.cmake#L114) custom target depends on the generated `Interfaces.h`.
- The generator itself is the `binding_generator` git submodule ([.gitmodules line 5](src:.gitmodules#L5): `[submodule "binding_generator"]`, url `git@github.sec.samsung.net:lws/binding_generator.git`).
- Generated sources are compiled into the engine via `FILE (GLOB STARFISH_SRC_GENRATED_BINDING ${OUTPUT_DIRECTORY}/starfish_generated/binding/generated/*.cpp)` ([`starfish.cmake`](src:build/starfish.cmake#L9)).

The JavaScript engine executing these bindings is the `third_party/escargot` submodule ([.gitmodules line 9](src:.gitmodules#L9), url `https://github.com/Samsung/escargot.git`).
